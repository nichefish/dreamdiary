# ITSM 로컬 보관·정제 계약

이 계약의 신뢰 판정은 [로컬 적재 신뢰 판정 공통 계약](LOCAL_INGESTION_TRUST_CONTRACT.md)을 따르되, 원격 동기화가 아니라 삭제 범위 승인과 실행 대상 동일성을 판정한다.

## 1. 범위와 목적

ITSM 원격 적재는 종료되었다. 이 계약은 `daily/text/raw/itsm/`에 이미 확보한 폐쇄형 로컬 아카이브의 분류, 이동, 삭제, 인덱스 동기화와 검증에만 적용한다. ITSM 웹사이트, 인증 URL, 목록·상세 화면과 첨부파일을 조회하거나 다시 내려받지 않는다.

아카이브의 목적은 전사 IT 지식의 보존이 아니라 사용자의 LIMSpro 경험, LIMS Jira 이력과 시험·품질·계측 업무 맥락을 보조하는 것이다. `LIMSpro`는 로컬 보존 말뭉치의 대표 폴더명이며, 원문에 기록된 `LIMS`, `구LIMS`, `NEW LIMS`, `LimsPro` 명칭과 시스템 필드는 당시 기록대로 보존한다.

## 2. 보존 판단

티켓은 다음 순서로 판정한다.

1. LIMS 본체의 원문인가?
2. 다른 시스템에 속하지만 LIMS의 기능, 데이터, 상태, 인터페이스, 장애 또는 업무 절차를 직접 다루는가?
3. 사용자가 보존 대상으로 합의한 LIMS 인근 시스템의 원문인가?
4. 원문을 제거하면 LIMS Jira·운영 이력의 의미를 해석할 수 없게 되는가?
5. 비LIMS 시스템에서 LIMS와 비교해 판단할 가치가 있는 시스템 병리를 입증하는가?

1~4에 해당하면 원문을 보존한다. 5에 해당하면 검증된 통찰과 그 주장을 입증하는 최소 원문만 보존한다. 어느 항목에도 해당하지 않으면 문서가 상세하거나 기술적으로 유용하더라도 삭제 대상이다.

`핵심 티켓`은 해당 시스템 담당자에게 중요한 티켓이 아니라 사용자 목적에 핵심인 티켓을 뜻한다. 장애 원인·조치, 시스템 설계, 인터페이스, 데이터 흐름과 업무 규칙이 상세하다는 사실만으로 비LIMS 원문을 보존하지 않는다.

## 3. LIMS 원문 보호

다음 원문은 개별 중요도와 반복 빈도에 관계없이 보존한다.

- 로컬 시스템 분류가 `LIMSpro`인 항목
- 다른 시스템에 속하더라도 본문이 LIMS의 기능, 데이터, 상태, 인터페이스, 장애 또는 업무 절차를 직접 다루는 항목
- 사용자가 별도로 전량 보존하기로 합의한 LIMS 인근 시스템의 항목

시스템 이름, GMP 적용 여부와 품질 부서의 사용 여부만으로 LIMS 관련성을 추정하지 않는다. 실제 데이터 객체, 상태 전이, 인터페이스 또는 업무 절차의 연결을 원문에서 확인한다.

## 4. 비LIMS 비교 증거

비LIMS 자료는 다음과 같이 LIMS를 판단할 때 비교 근거가 되는 시스템 병리를 입증하는 경우에만 보존한다.

- 소스 코드, 빌드 산출물 또는 배포 이력의 유실
- 감사추적, 전자서명 또는 전자기록의 무결성 결함
- 규제 대상 데이터나 업무 이력의 비가역적 유실·훼손
- 지원되는 복구 경로가 없어 운영 DB를 직접 수정해야 하는 상태
- 검증되지 않거나 추적할 수 없는 배포와 설정 불일치
- 특정 담당자나 벤더에게 지식·권한이 집중되어 운영 또는 설명이 불가능한 상태
- 여러 시스템에서 수치와 기간으로 확인되는 동일한 조직적 실패

시스템별 사용법, 정상 업무 로직, 설계 설명과 일반 장애 해결법은 비교 병리가 아니다. 보존할 때는 통찰을 먼저 명시하고 관측 사실·영향·원인 또는 대응을 입증하는 가장 작은 원문 집합만 연결한다.

## 5. 운영성 항목

다음 항목은 개별 보존 가치가 낮은 운영성 후보다.

- 계정·권한·비밀번호·담당자 변경
- 데이터 수정·삭제·추출
- 처리 결과가 없거나 `완료했습니다`와 같은 짧은 결과만 있는 문서
- 테스트·중복·재문의
- 개인 PC·클라이언트 설치·접속 지원
- 특정 건의 값만 바꾸는 일회성 작업

LIMS와 합의된 인근 시스템에서는 반복 군집이 필요한 운영 맥락을 제공할 때 검증된 패턴 문서를 남기고 개별 원문을 삭제할 수 있다. 반복 군집이 아니거나 사용자에게 필요한 맥락이 아니면 패턴 문서 없이 삭제한다. 비LIMS 시스템에서는 반복된다는 이유만으로 패턴 문서를 만들지 않는다.

## 6. 판정 보조자료

중요도 인덱스, 제목 키워드, 본문 길이, 처리 결과의 상세도, 요청 공수와 담당자 유형은 검토 순서를 정하는 보조자료다. 어느 것도 보존·삭제의 단독 근거로 사용하지 않는다. 중요도 점수는 기술적 정보량을 나타낼 수 있지만 사용자 관련성을 나타내지 않는다.

## 7. 파일과 인덱스

- 원문 루트: `daily/text/raw/itsm/`
- 통합 인덱스: `daily/text/raw/itsm/index.json`
- 중요도 인덱스: `daily/text/indexes/itsm-importance/`
- 정제 판정: `daily/text/indexes/itsm-curation/system-flags.md`
- 패턴과 통찰: `daily/text/indexes/itsm-patterns/`

Markdown 티켓과 해당 티켓에 연결된 이미지(`.png`, `.jpg`, `.jpeg`)만 원문 아카이브에 둔다. 동영상, 오피스 문서, PDF, 압축파일과 과거 수집 로그·체크포인트는 보존하지 않는다. 시스템별 폴더는 사용자가 인지하는 대표 시스템명으로 통합하고, 원문의 시스템명 필드는 바꾸지 않는다.

## 8. 변경 절차

분류·이동·삭제 전에 다음을 확인하고 사용자 승인을 받는다.

1. 대상 폴더와 실제 티켓 수
2. LIMS 직접 관련 문서의 존재 여부
3. 비교 병리와 이를 입증하는 최소 원문
4. 삭제할 원문·연결 이미지·패턴 문서의 정확한 범위
5. 변경이 통합 인덱스와 중요도 인덱스에 미치는 영향

삭제 승인은 경로, 파일 byte 길이와 SHA-256을 정렬한 manifest의 SHA-256에 결박한다. 승인 직전 manifest와 실제 삭제 직전 같은 방식으로 다시 계산한 manifest가 byte 단위로 동일하고 다음 명제가 모두 `TRUE`일 때만 삭제할 수 있다.

```text
approvedManifestHash == currentDeletionTargetManifestHash
manifestEntryCount   == currentDeletionTargetCount
manifestMissingCount == 0
manifestExtraCount   == 0
```

어느 값이든 관측할 수 없으면 `UNKNOWN`이며 삭제하지 않는다. 경로·길이·파일 SHA-256이 하나라도 달라지면 새로운 manifest로 다시 승인받는다. AI의 내용 유사성 판단으로 manifest 불일치를 승인 범위에 포함하지 않는다.

승인된 변경은 다음 순서로 수행한다.

1. 보호 대상 문서와 연결 이미지를 `LIMSpro` 또는 합의된 폴더로 이동한다.
2. 비교 병리를 설명하는 통찰과 최소 증거의 연결을 검증한다.
3. 승인된 원문과 연결 파일을 삭제한다.
4. 빈 폴더와 가치가 사라진 패턴 문서를 제거한다.
5. 통합 인덱스, 중요도 인덱스와 정제 판정을 현재 파일 집합에 맞춘다.

삭제된 원문의 목록이나 `DELETED` 표식은 남기지 않는다. Git이 추적하지 않는 원문 삭제는 복구할 수 없으므로 대상 확인과 승인을 생략하지 않는다.

## 9. 완료 검증

- 원격 ITSM 요청이 발생하지 않았는지 확인한다.
- `index.json`의 각 Markdown 경로가 실제 파일과 일치하는지 확인한다.
- 중요도 인덱스가 실제 Markdown 티켓과 일대일로 대응하는지 확인한다.
- 정제 판정의 시스템별 건수가 실제 폴더와 일치하는지 확인한다.
- 패턴·통찰 문서의 원문 링크가 모두 유효한지 확인한다.
- 원문 루트에 허용되지 않은 확장자와 수집 로그·체크포인트가 없는지 확인한다.
- 승인 manifest hash와 삭제 직전 manifest hash가 동일했는지 확인한다.
- `python scripts/check_encoding.py`를 실행하고 한글이 포함된 변경 파일의 `git diff`를 확인한다.
