# Keep 리마인드 푸시 정책 초안

> 상태: 확장 아이디어 (계약 외부) — 현재 고정 정책·서버 기반의 정본은 [Prospective 인터랙션 spec](../migration/prospective/interaction-spec.md)의 Keep 서버 리마인드 항목이다. 이 문서는 추가 합의가 필요한 확장 후보와 설계 쟁점만 다룬다.
> 대상: DreamDiary Keep (`prospective_keep`, 콘텐츠 유형 `PROSPECTIVE_KEEP`)
> 작성: 2026-10-14

## 1. 목적

사용자가 Keep의 할 일을 계속 기억하고 있지 않아도 적절한 시점에 다시 인지하고 실행할 수 있도록 한다. 반복적인 주의 환기보다 미래 행동의 적시 재인식을 목표로 한다.

## 2. 현재 구현과 날짜 의미

현재 구현은 서버 고정 정책·기기 IANA 시간대·Expo 푸시를 사용한다. 앱은 인증 기기 등록과 해제, 권한 변화 반영, 알림 선택 후 최신 대상 목록을 연결한다. 외부 전달 검증에는 SQL 수동 적용과 Expo/FCM 구성이 필요하다. 현재 계약은 다음 문서를 따른다.

- [모바일 화면 spec §4.14](../migration/mobile/screen-spec.md)
- [Prospective 인터랙션 spec](../migration/prospective/interaction-spec.md)
- [모바일 Keep 계획](../migration/mobile/keep-todo-plan.md)

`expireDt`는 현재 유효 기한이며 시각을 갖지 않는다. `dateText`는 자유 입력 일시이고 클라이언트가 마지막 유효 날짜를 추출해 기한을 확정한다. 실행 예정일·일정의 시작/종료 시각과 유효 기한의 구분은 알림 확장 전에 검토할 필요가 있다.

이 초안의 D-Day는 잠정적으로 유효 기한을 기준으로 설명한다. 예정일을 알림 기준으로 사용할지는 별도 결정 사항이다. 일정 도메인과 Keep의 관계는 [일정·TODO 존재론](schedule-todo-ontology.md), Keep의 상태·기한 축은 [Keep 존재론](prospective-keep-evolution.md)을 함께 참고한다. 두 문서의 수렴 방향도 아이디어이며 확정 계약으로 취급하지 않는다.

## 3. 논의에서 도출한 방향

다음은 문서에 남기는 논의 방향이며 구현 계약으로 승격하려면 추가 합의가 필요하다.

- 리마인드의 기준 날짜와 대상 상태를 명시한다.
- 완료·보류·삭제와 종결 상태를 발송 대상 판단에 반영한다.
- 이미 지난 알림 시점은 소급 발송하지 않는다.
- 같은 발송 시점의 항목은 가능한 한 요약 알림으로 묶는다.
- 알림 권한 거부·전달 실패는 Keep의 원본 데이터와 상태를 변경하지 않는다.
- 앱이 실행 중이지 않을 때도 알림을 받을 수 있는 전달 구조를 검토한다.
- 서버 푸시는 발송 직전에 서버의 최신 상태와 날짜를 확인하는 방향으로 설계한다.

## 4. 알림 강도 확장 후보

일반·중요(IMPRTC)의 고정 일정과 OPEN 발송·보류/종결 제외·재개 처리는 현재 계약의 spec을 따른다.

긴급 구분은 새 후보이며 사용자가 명시적으로 선택한 항목에만 적용하는 방향을 제안한다. 긴급 후보는 D-3부터 D-Day까지 매일 아침·저녁 알림을 검토할 수 있다. 중요 표시를 긴급으로 자동 해석하지 않는다. 긴급의 저장 구조·사용자 선택·개별 알림 여부는 미결정이다.

## 6. 최신 상태와 전달 보장 경계

서버는 발송 요청 직전에 인증 소유 기기와 최신 OPEN·중요·기한을 확인한다. 앱은 알림 선택 시 현재 인증 계정의 최신 대상 목록을 서버에서 다시 조회한다. 이 범위의 슬롯 기록·중복 방지·해제·빈 목록 처리는 spec의 현재 계약을 따른다.

최신 상태 확인과 외부 푸시 요청 사이에도 상태 변경이 발생할 수 있다. 전달 서비스와 OS의 지연 때문에 화면 표시 순간의 상태와 발송 직전 확인 상태가 다를 수 있다. 이미 전달된 알림의 회수·추가 전달 보장·재시도 전략은 별도의 합의가 필요한 확장 후보다.

DB 발송 시도 기록 후 외부 요청 전에 서버가 중단되면 해당 슬롯은 누락될 수 있다. 현재 계약의 재전송 금지와 별개로 전달 보장을 높일지는 실패 비용과 중복 위험을 함께 검토한다.

## 7. 묶음과 알림 선택 동작

동일 사용자·동일 발송 시점의 알림은 하나의 요약 알림으로 통합하는 방향을 제안한다.

예시 (가상 집계):

- 오늘 기한: 3건
- 내일 기한: 2건
- 3일 후 기한: 1건

고정 제목·개수 요약·알림 선택 후 최신 대상 목록·대상 소멸 시 빈 목록 표시는 현재 spec의 계약을 따른다. 개수 외 추가 표시 정보와 세부 묶음 확장은 별도 검토한다.

항목 ID·본문·제목을 푸시 payload와 잠금 화면에 얼마나 노출할지는 별도 검토한다. 긴급 후보의 개별 알림 허용 여부와 묶음 기준은 미결정이다.

## 8. 시각·시간대 제안

- 아침: 09:00
- 저녁: 19:00
- 시간대: 사용자 로컬 시간대

09:00·19:00과 기기 IANA 시간대는 현재 spec의 고정 계약이다. 앱 전경 복귀에서 기기의 현재 시간대를 다시 등록한다. 사용자별 시각 변경·여러 기기에 적용하는 공통 시간대 관리·앱을 열지 않은 여행 중 시간대 변화 처리는 후속 검토 사항이다.

## 9. 향후 결정 사항

- 실행 예정일과 유효 기한의 구분 및 알림 기준 날짜
- 날짜 없는 Keep의 알림 여부
- D-Day 이후 미완료 항목 재알림
- 반복 할 일의 생성·알림 정책과 데이터 모델(데일리 루틴은 Keep 범위 제외)
- 추가 알림 강도·긴급 구분
- 사용자별 아침·저녁 시각 변경과 기기별 시간대를 넘어서는 사용자 공통 시간대 관리
- 묶음의 범위·표시 내용·긴급 개별 발송
- 알림 대상 목록의 추가 UX
- 개수 요약을 넘어서는 잠금 화면·payload 정보 확장
- 현재 Expo 전달·발송 기록 계약을 넘어서는 재시도·전달 보장 전략
- 로컬 예약 수렴 이후 추가 기기 관리·알림 UX 확장

## 10. 설계 경계

이 문서는 Keep 리마인드 푸시의 정책 후보와 검토 경계를 소유한다. Keep 저장 구조, 일정 도메인 수렴, 반복 일정 모델은 각각의 설계 논의에서 다룬다. 데일리 루틴은 Keep에서 관리하지 않는다.

추가 합의 전에는 위 제안을 기능 spec의 구현 예정 항목으로 등재하거나 기존 알림 계약을 바꾸지 않는다. 합의된 범위가 생기면 해당 범위를 현재 계약의 spec에 반영하고 구현·검증을 진행한다.
